## Accessibility and signing

- Window tracking, focusing and minimizing depend on macOS Accessibility permission. The app checks `AXIsProcessTrusted()` and displays a warning if it is false.
- A recurring failure was an enabled Accessibility switch while the app still reported no access. The app running at the path in `build` was the correct build. TCC logs showed that the system `tccd` service was checking an old cached code hash (`37a979...`) against the newer build. Removing and re-adding the old entry did not solve it.
- Changing the bundle identifier from `local.dan.windows-qol` to `local.dan.windowsqol`, rebuilding, and registering the new app for Accessibility resolved this for Dan. The app migrates pinned apps and the pending Dock backup from the old preferences domain. The bundled Finder extension also has a new identifier.
- The local build is ad-hoc signed with an explicit, stable identifier-based designated requirement; it is not an authenticated developer signature. Do not assume this alone prevents TCC cache issues across rebuilds. If access fails again, check the actual running executable, its code signature, and relevant `com.apple.TCC` logs before recommending another permission reset. Never modify the TCC database directly or weaken macOS security to fix it.
- The first build under a new identity requires the user to grant Accessibility in System Settings. Only the user can grant it. The taskbar can be present even while access is denied.
- Settings → Permissions checks Accessibility and screen capture and requests access through macOS APIs. A direct screen-capture request still failed to create a visible entry in System Settings on Dan's Mac; macOS owns the list. The user added the app with the + button and reported that it worked. Do not promise that requesting access will automatically add an entry.

## Native Dock

- macOS has a single native Dock, and there is no reliable public API here for assigning it to the monitor whose taskbar button was clicked. Do not promise per-monitor native Dock control.
- The rightmost button toggles the global Dock auto-hide setting using System Events; the former implementation restarted Dock on every click and caused visible flicker. macOS may ask for Automation permission.
- To suppress accidental edge reveals, the app temporarily sets the undocumented global `autohide-delay` to 1,000 seconds. On a normal quit, it restores the saved previous delay and makes the native Dock visible, restarting Dock once to apply the change. Preserve the backup and do not overwrite later user changes to the delay. A crash or force quit cannot run normal shutdown cleanup; reopen and quit normally to recover. For immediate recovery, `defaults write com.apple.dock autohide -bool false && killall Dock` makes the Dock visible.
- The app hides the Dock on startup. The ▣ menu's Reload option performs a normal quit and launches the app again; the Dock can briefly reappear and restart during this process. Dan confirmed both behaviors work.
- Dan confirmed the Dock toggle worked and the old process-restart implementation flickered. The newer System Events toggle and shutdown cleanup require interactive verification when changed; do not describe compilation alone as proof.

## Finder and taskbar behavior

- Finder icon view with **Sort By → Name** naturally reflows icons when resized and sorts newly added items. It is distinct from manually positioning icons with Snap to Grid; a custom reflow feature is unnecessary for this use case.
- `Sources/FinderExtension.swift` provides an `Open Terminal Here` Finder Sync extension for the background context menu. Finder extensions may require explicit enablement and may not appear for virtual or cloud-provider folders. Registration/build success is not proof the menu action works interactively.
- Dan confirmed the Terminal action works. Finder's sandbox denied the extension permission to hand a folder directly to Terminal, so the extension sends the folder path through the `windowsqol-terminal` URL scheme to the main app, which validates the path and opens it in Terminal. Finder may cache the old extension identity after a rebuild; its logs exposed a failed connection to the old identifier. Re-registering the extension and restarting Finder refreshed it. A duplicate menu entry occurred when Finder had started two instances of the same registered extension; restarting Finder left one instance and resolved the duplicate. Restarting Finder can disrupt open Finder windows, so explain it when needed.
- Taskbar windows are tracked per display through Accessibility. Minimized windows retain their last known display while the app is running; windows already minimized at startup may not have usable coordinates. Apps with multiple local windows show a stacked icon; hovering or clicking opens a horizontal preview chooser, and never minimizes a window directly. A single active window's icon minimizes it; restoring returns it to its previous size, not necessarily maximized. Previews use ScreenCaptureKit when permission and a unique window match are available, and otherwise show the app icon. Allow time and space for pointer movement into the chooser. Dan confirmed this behavior and styling worked.
- Terminal and System Settings icons at the right of the taskbar are monochrome quick launchers. Their running windows appear among normal apps on the left; the right-side buttons do not minimize or act as running-app icons.
- Pinned apps stay on the primary bar and can be pinned or unpinned from an icon's context menu and reordered by dragging. Finder with no local window creates a new Finder window and attempts to place it on the clicked display; other apps with only remote windows show a chooser instead of silently switching screens. The taskbar uses a bold blue underline for visible local windows, a dim thin underline for minimized-only windows, and a brighter line for focus. Stacked icons are equal-sized copies of the real icon, consistently offset; generic rounded backplates looked wrong to Dan. Dan approved the revised appearance.
- macOS does not reserve desktop space for the custom taskbar. The app uses Accessibility to shorten windows that span almost the full display height so their bottom edge sits above the bar. It waits until mouse dragging ends and skips macOS full-screen Spaces; ordinary windows and apps that refuse resizing may still overlap. Dan confirmed this works for his setup.
- The optional Windows-style Fn shortcuts use an Accessibility event tap. Fn-C/A conflict with native Control Centre/Dock shortcuts. Fn-S captures the display under the pointer via `screencapture` and requires screen-capture permission; Fn-Shift-S invokes macOS's area screenshot to the clipboard. Fn-E opens Finder and may need Automation permission. The screenshot and permission flow was reported working after manual permission setup; do not infer that every shortcut or monitor arrangement has been individually tested.
